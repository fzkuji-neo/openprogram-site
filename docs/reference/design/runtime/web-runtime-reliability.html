Web Runtime Reliability and Performance Design

This document consolidates verified issues in Web refresh, session loading, WebSocket distribution, background-error display, EventBus notifications, asynchronous Job state, static assets, and local state directories, defining compatible target contracts, task boundaries, and quantitative acceptance criteria.

Audience: Runtime / Server / Web maintainers Status: TASK 1 partial; TASK 3 complete; TASK 6 complete; remaining tasks pending Evidence: source audit, real-session measurements, browser measurements, focused tests
Main conclusion: Missing durable error state, duplicate full-session refreshes, and potentially blocking/lost EventBus notify remain P0. Command exception isolation and the first management-action migration are complete in two slices; other legacy error/recovery paths remain. TASK 3 resolves unbounded WebSocket broadcasting and passes specification, quality, and full Python gates. TASK 6 completes local dependencies, static compression, lazy surface splitting, and resource budgets with both reviews, full Python, default-App visual acceptance, and local browser traces.
Scope boundary: No changes to Agent reasoning, DAG storage semantics, provider protocols, permission models, or multi-user identity. Existing topic documents retain detailed semantics; this page defines their shared Web reliability/performance contracts.

04

Unified error contract and frontend display

“Backend errors must appear in frontend” means every failure affecting user requests, durable state, background tasks, or recoverable operations produces an observable error record. It does not mean every internal retry/degradation becomes a Toast, nor permit traceback, file content, or credentials in browsers. This schema is the sole final wire contract. TASK 1 server generates complete fields for public dispatcher/initial management actions, records before sending, and supports principal-scoped list, exact-ID acknowledgement, and multi-window recovery. Frontend hydration/display and other sources remain later slices.

Server normalization

One safe payload builder

The helper generates filtered error data and validates fields, log correlation, and session routing. WS action/channels/system wrap it as operation_error; JobRunner embeds the same data in the sole job_status, without a second error envelope.

Frontend error store

One state entry

use-ws parses and forwards to the error store only; cards, session markers, and Toasts derive from one record rather than independently interpreting codes.

Action correlation

Explicit request completion

Request/response actions use request IDs. Success and failure end pending; no button may load indefinitely.

Compatibility adapter

Incremental legacy-frame migration

During migration, frontend adapts existing error, action_error and Job errors into unified records; remove compatibility branches after each backend migration.

Separating computation from sending

A synchronous thread reads an immutable SessionDB snapshot, builds ID indexes, current chain, and Graph summary, returning plain objects. Async handler rechecks revision before sending; concurrent writes cause manifest-plus-delta or a fresh snapshot. Threads never manipulate WebSockets.

Duplicate computation to remove

Prebuild id → insertion_index instead of sorting with all_msgs.index; group siblings once by predecessor; read the session row once per request; serialize Graph summary separately from message bodies.

Large fields and compatibility

Preserve current 32 KiB tool-result markers and get_full_tool_output authorization checks. Extend on-demand reads to context trees, runtime blocks, Graph-node content, and attachment metadata. Legacy clients may request old actions, but server payload caps must return upgrade guidance rather than unbounded frames.

WebSocket queues, ordering, and recovery

Standard browser WebSocket APIs provide no automatic backpressure, so servers must bound send queues. One sender task per connection sends sequentially; producer threads only enqueue thread-safely.

Frame categoryExampleQueue ruleOverflow behavior
Non-droppable terminalerror, question, chat final, job terminal, ack, permission resultPreserve order; no overwriting or cross-session merging.If queue budget is unavailable, close and require state recovery; never drop silently.
Coalescible deltatext/thinking delta, tree update, progress, context statsBy session + entity + type, keep newest state or merge adjacent text.Remove superseded deltas and increment coalesced counts.
Snapshotsessions list, branches, settings, graph summaryKeep only the newest unsent snapshot per key.Replace old snapshots without affecting terminal frames.
Controlpong, auth/status, reload requiredSmall separate budget prevents large-message starvation.Authentication/protocol errors close immediately; stale pong values may be discarded.

Queue limits and critical reserve

Per connection: 256 frames or 4 MiB, whichever first; reserve 64 frames and 1 MiB for non-droppable terminal events. Before critical enqueue, remove coalescible deltas; do not consume old ordinary snapshot versions.

Send ownership

Only sender task calls ws.send_text. On disconnect, cancel sender, free queue, and unregister focused session; other threads retain no WebSocket Futures.

Reconnect

Exponential backoff with jitter; page visibility or explicit retry may trigger earlier. Restore protocol state before session projection.

Metrics

Record queue_frames, queue_bytes, oldest_age, coalesced, send_failures, disconnect_reason, and recovery_mode without frame bodies.

Critical-frame recovery contract: Sources persist chat final, Job terminal, user-visible error, question, and permission requests before enqueue. All user-visible errors also enter bounded UserErrorStore, queried by error_id, retaining at most 1,000 records or 7 days. Session manifests include only relevant open IDs; reconnect reads details through list_user_errors(cursor). Clients derive transport-close state locally from close/timeout, independent of server error frames. Chat ack follows durable user-message storage; other request acks must be idempotently queryable/replayable by request_id. If critical reserve is still full, close the connection and mark state_recovery_required; reconnect restores from manifest, UserErrorStore, pending-question registry, Job store, and request-result queries, not unsent memory frames.
MDN WebSocket

Standard WebSocket has no automatic backpressure. Retain its broad compatibility while bounding application queues.

MDN bufferedAmount

Clients can use bufferedAmount to monitor unsent bytes, but it cannot replace server per-connection queues and recovery.

Python asyncio.Queue

Use a FIFO queue with positive maxsize; cross-thread callers use event-loop thread-safe scheduling, never direct cross-thread Queue manipulation.

09

Runtime metrics, capacity, and state directories

Performance changes must remain measurable on the default worker. Record counts, durations, bytes, and correlation IDs only, not prompts, model responses, tool output, or credentials.

WebSocket

  • Active connections and queue bytes per connection.
  • Send latency, failures, coalesced count.
  • Reconnect counts, recovery mode, full-recovery reasons.

Session hydration

  • Separate manifest/messages/graph bytes.
  • DB read, projection, serialization, and send durations.
  • Viewport hits, detail fetches, delta fallbacks.

EventBus

  • Notify enqueue and handler duration.
  • Queue depth, failures, retries, drop reasons.
  • Total gate time and budget overruns.

Storage

  • Categorized sessions, logs, Chrome cache, models, and IndexedDB sizes.
  • Show target and impact before user-triggered cleanup.
  • Do not delete cookies, login state, extensions, or sessions by default.
Cleanup boundary: Browser profiles are user state and must never be auto-deleted by background timers/startup hooks. List rebuildable cache/models separately from identity/extensions/IndexedDB and require explicit category confirmation.

Bounded session history

Session loading separates the latest transcript page from older history. Pages retain their captured branch head and a stable oldest-message cursor. A page contains complete display rows and their caller descendants, with at most 50 top-level rows and a 512 KiB target serialized budget. One indivisible larger row is returned alone. Paging never edits stored history or model context. Historical reads do not change focus, live session head, execution state, or question replay.

Codex separates thread metadata, turns and items through paginated history APIs. DeepSeek Harness exposes message-aligned pages and sequence cursors. This implementation adopts stable branch snapshots, backward paging and incremental live updates; it retains OpenProgram's existing branch graph and execution recovery contracts. It does not introduce another session store or change model compaction.

Duplicate promoted fields are omitted from the wire-only extra object. Existing tool-output previews retain their authorized full-output expansion. Logical history and graph responses larger than the transport frame budget are sent as ordered, awaited fragments; the client reconstructs a complete response before dispatch, preserving first-fragment order with subsequent live notifications. Deferred responses share a per-connection budget of 64 million UTF-16 code units, eight incomplete transfers and 1,024 logical responses. This handles a single large row without silently dropping data or increasing the 4 MiB sender queue. Ordinary live updates continue independently. Fragment buffers belong to one connection and are discarded on disconnect. Reconnect loads a fresh recent page and uses existing execution recovery.

The client prepends older rows by stable identity without replacing newer live content or moving the selected conversation. Page requests capture the current load generation and are ignored after a reload, branch switch or socket replacement. An unavailable cursor produces an explicit retryable error instead of a reconnect loop. Scroll position remains anchored when older messages are inserted. The graph remains complete for existing branch and compaction controls; server-side history projection still scans the captured session. Storage indexing and lazy graph rendering are separate optimizations, not claimed here.

Acceptance: the copied failing session opens without queue overflow; every logical page retains exact content and caller ownership; page frames stay bounded, including Unicode and a single oversized row; cursor exhaustion loses or duplicates no messages; stale responses cannot overwrite live/newer state; disconnection releases partial buffers; branch, compaction, tool expansion and execution recovery remain functional. Implementation status: implemented and independently reviewed. The combined verification passes 8,591 Python tests, 635 Web tests, four browser tests and 190 CLI tests, together with Desktop, static, type, build and documentation checks. The installed App retrieves all 26 original display rows in five pages without duplicates, reordering or disconnects; the largest observed transport frame is 51,564 bytes. Reload and heartbeat remain operational.

Long-session layout and loading

The bounded history protocol separates transport size from transcript length. Long sessions also require stack-safe graph construction: the depth pass previously followed every ancestor for every node and recursively visited the conversation chain. A 1,500-node linear conversation exceeds Python's recursion limit before its first page can be delivered.

Graph depth now uses a memoized parent-chain classification followed by iterative preorder traversal. Nodes whose parent path enters a cycle remain independent roots, preserving the existing defensive behavior. Forks, retries, spawned branches and call children retain their current row order and offsets. Parent classification visits each node once; traversal does not depend on the Python call stack. Follow-up normalization indexes replies once. Lane column placement maintains per-lane widths and the largest occupied column rather than rescanning previously placed nodes.

Session message aggregation and byte-budget page preparation execute outside the event loop, while awaited WebSocket sends remain on the owning loop. Branch graph construction also executes outside that loop. Snapshot and incremental event ordering remain unchanged. The existing in-memory session index remains authoritative for reads; this change introduces no persistent cache, schema migration or history deletion.

Acceptance uses the public graph builder and session-loading handler with long chains, wide fork sets and invalid cycles. Small-graph output must match existing layout contracts, and a 10,000-node transcript must load a bounded recent page without recursion failures. Full graphs and initial store indexing remain proportional to session size; this work does not claim constant-memory storage or indexed transcript projection. The Codex and DeepSeek references in the bounded-history section continue to define the paging comparison.

Implementation status: implemented and independently reviewed. Public layout and session-loading tests cover a 10,000-node chain, wide forks and invalid cycles; complete graph output and bounded transcript pages are preserved. The combined verification and installed-App long-history replay pass. Initial graph and store memory still grow with session size.
